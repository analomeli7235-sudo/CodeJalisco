# Community Connect

Estoy trabajando en una tarea universitaria del curso Uso de Big Data para la Toma de Decisiones, correspondiente a la carrera de Desarrollo de Sistemas Web.

La actividad tiene como objetivo documentar el Product Backlog, el Sprint Planning, los resultados obtenidos durante el desarrollo del primer sprint y los resultados de la reunión retrospectiva, incluyendo las conclusiones y las posibles modificaciones o ajustes que deberán considerarse para el siguiente sprint.

Objetivo de la actividad.                                                                                                                                                  Contexto del proyecto.

Nombre del proyecto.

CodeJalisco: Plataforma ciudadana para el reporte de problemas urbanos.

Contexto.

El proyecto consiste en crear una plataforma dirigida a los ciudadanos y autoridades/dependencias responsables para que puedan reportar problemas de su comunidad de manera fácil y rápida, como baches, fallas en alumbrado público, árboles caídos, acumulación de basura, fugas de agua, entre otros.

La plataforma permitirá enviar el reporte, agregar una fotografía y ubicación, y posteriormente consultar su estado.

Problema.

Actualmente, reportar un problema de la ciudad puede ser complicado porque el ciudadano muchas veces no sabe a qué dependencia acudir o qué medio utilizar.

Esto puede provocar que los problemas tarden en ser atendidos o que los ciudadanos simplemente no los reporten.

Solución propuesta.

La solución propuesta consiste en desarrollar una plataforma digital donde los ciudadanos puedan reportar de manera fácil y rápida problemas de su comunidad como:

- Baches.

- Fallas en el alumbrado público.

- Árboles caídos.

- Acumulacion de basura.

- Fugas de agua.

El sistema permitirá al usuario:

- Registrar el problema.

- Agregar una fotografía.

- Indicar la ubicación.

- Enviar el reporte. 

Además, podrá recibir un folio para consultar posteriormente el estado de su reporte y conocer si ya fue atendido.

3. Sprints y su distribución.

El proyecto se dividirá en ocho Sprints de dos semanas, completando un periodo de 16 semanas. La distribución seguirá un avance progresivo, comenzando con la definición del proyecto y terminando con la validación y preparación del prototipo final.

- Sprint 1: análisis, requisitos, Product Backlog y planeación inicial.

- Sprint 2: diseño de interfaz, estructura y navegación.

- Sprint 3: registro, inicio de sesión y perfiles.

- Sprint 4: registro de problemas, categorías, descripción y fotografías.

- Sprint 5: ubicación, generación de folios y consulta de reportes.

- Sprint 6: seguimiento y actualización de estados.

- Sprint 7: panel administrativo y pruebas integrales.

- Sprint 8: correcciones, pruebas de aceptación, documentación y entrega final.

Esta distribución permite que las funcionalidades principales no se desarrollen todas al mismo tiempo, sino de manera gradual, facilitando la revisión de cada incremento. Necesito desarrollar y documentar el primer sprint del proyecto , generando un código funcional que pueda alojarse en GitHub para que sea posible revisarlo y comprobar su funcionamiento.

El código debe:

- Corresponder a las actividades y objetivos definidos para el primer sprint.

- Tener una estructura clara, organizada y coherente.

- Ser funcional y no presentar errores de código.

- Poder ejecutarse y revisarse correctamente.

- Mantener una estructura original que demuestre comprensión de los conceptos abordados en el curso.

- Estar preparado para publicarse en un repositorio de GitHub.

Además del código, necesito elaborar la documentación correspondiente al sprint, incluyendo una breve explicación de lo realizado, los resultados obtenidos y los aspectos identificados durante la reunión de retrospectiva.

Elementos que debe incluir la propuesta.

Considera los siguientes apartados:

1. Sprint Planning.

   - Definir claramente el objetivo del primer sprint.

   - Indicar las actividades o tareas que se planificaron.

   - Relacionar las actividades con los elementos correspondientes del Product Backlog.

   - Explicar brevemente qué se esperaba obtener al finalizar el sprint.

2. Desarrollo y resultado del primer sprint.

   - Generar el código correspondiente al primer sprint.

   - Explicar de manera breve y clara qué se desarrolló.

   - Indicar cómo funciona el código y cuál es su propósito.

   - Señalar los resultados obtenidos al finalizar el sprint.

   - Procurar que el código sea funcional, revisable y libre de errores.

   - Indicar la estructura de archivos y carpetas utilizada, explicando brevemente la función de los elementos principales.

   - Preparar el proyecto para su publicación en GitHub.

3. Repositorio de GitHub.

   - Proporcionar el enlace al repositorio de GitHub donde se encuentre alojado el desarrollo del primer sprint.

   - El repositorio debe estar organizado de manera que facilite su revisión.

   - Incluir, cuando sea necesario, un archivo README con las instrucciones básicas para comprender, instalar, ejecutar y revisar el proyecto.

4. Reunión retrospectiva.

   - Documentar los resultados de la reunión retrospectiva.

   - Indicar qué aspectos del sprint funcionaron correctamente.

   - Identificar las dificultades, problemas o áreas de oportunidad encontradas durante el desarrollo.

   - Explicar qué aprendizajes se obtuvieron.

   - Establecer conclusiones claras y coherentes sobre el trabajo realizado.

5.Modificaciones o ajustes para el siguiente sprint.

   - Identificar las modificaciones, mejoras o ajustes que se propongan a partir de la retrospectiva.

   - Explicar por qué se considera necesario realizar cada ajuste.

   - Indicar cómo estas modificaciones pueden mejorar el desarrollo del siguiente sprint.

   - Relacionar los ajustes con las actividades o elementos que deberán abordarse posteriormente.

Recomendación de la actividad.

Es importante no olvidar incluir el Sprint Planning, el resultado del desarrollo del sprint y el resultado de la reunión retrospectiva, acompañados de las conclusiones correspondientes y de una explicación clara cuando existan modificaciones o propuestas de mejora para el siguiente sprint.

Criterios de evaluación.

La actividad será evaluada considerando los siguientes criterios:

- Definir con claridad el Sprint Planning.

- Presentar el enlace de GitHub con el desarrollo del primer sprint.

- Documentar el resultado de la reunión retrospectiva.

- Establecer de forma clara y coherente la propuesta de modificaciones o ajustes para el siguiente o siguientes sprints.

Requisitos de presentación.

Asegúrate de que tanto la estructura del código como la estructura del documento sean originales, ordenadas y coherentes, y que demuestren un entendimiento real de los conceptos relacionados con la actividad.

La propuesta debe mantener un enfoque académico, pero utilizar explicaciones claras y comprensibles, evitando incluir contenido innecesariamente técnico. El resultado debe quedar organizado de manera que pueda utilizarse como base para la entrega universitaria y permita identificar claramente la relación entre el Product Backlog, Sprint Planning, desarrollo del sprint, retrospectiva y ajustes para los siguientes sprints.
